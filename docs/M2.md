## M2-00-B 本次实现内容

用户从 M1 设备列表里**手动连接**当前已选的组网 IP 或内网 IP 后，点击「M2 能力预检」。这个操作：

1. 使用现有 `X-EasyADB-Token` 鉴权与按设备 ID 的互斥锁；
2. 确认当前选择的 `selected_serial` 已由本会话的 M1 管理器记录为已连接，并显式执行一次 `adb get-state`；
3. 只读执行 `getprop ro.build.version.sdk`、`ro.product.cpu.abi`、`ro.product.model` 和 `wm size`，返回基本设备信息；
4. `stream_verified=false` 明确表示**尚未证明设备编码器、浏览器解码或 scrcpy 协议可工作**。

不会后台定时检查、自动连接、自动换地址、重试配对、`adb push`、创建端口转发、运行手机端进程或修改设备数据库。没连接时返回 HTTP 409。前端以文字形式展示结果，切换设备或地址后清空旧结果。

## M2-00-C/D 视频链路实验（本次实现，真机待测）

scrcpy 来源：[官方 v5.0.1 发布页](https://github.com/Genymobile/scrcpy/releases/tag/v5.0.1)，固定文件 `scrcpy-server-v5.0.1`，GitHub 官方发布资产 SHA-256：

```text
764eb6f79811d5211fe9df341120882ba9994c7a61b897d7bf3fb662e53bc536
```

构建镜像时从官方地址下载服务器文件并执行 `sha256sum -c`，不匹配即阻止构建；同版本 `LICENSE` 一同放进镜像 `/opt/easyadb/scrcpy/`（Apache-2.0）。**本次固定的协议解析仅适用于 v5.0.1**，未来升级必须连协议解析和测试一起复核，不会执行“latest”版本的动态下载。

在已明确手动连接的当前选择设备上点击「视频实验 · 基础」或「视频实验 · 原生」，调用需认证的 `POST /api/devices/{id}/m2/video-probe`，请求字段 `{"profile":"baseline"}` 或 `{"profile":"native"}`：

| 档位 | max_size | 目标码率 | max_fps | 降尺寸回退 |
|---|---:|---:|---:|---|
| baseline（基础） | 最大边 1600 | 8 Mbps | 30 | 关闭 |
| native（原生参数） | 0（不限制尺寸） | 16 Mbps | 30 | 关闭 |

实验由用户主动发起。后端仅对已保存 `selected_serial` 做一次 `get-state`，使用每次随机的 scrcpy SCID / Android 临时 jar 路径，通过 `adb -s <当前地址> forward tcp:0 localabstract:scrcpy_<SCID>` 获得宿主机回环端口，再以 `video=true audio=false control=false tunnel_forward=true` 启动固定版本服务器。先收发 dummy handshake、64 字节设备名、4 字节 codec 标识、12 字节会话尺寸头，再按 scrcpy v5.0.1 内部帧协议解析 H.264 config/media/key frame 等元数据，最多读取 48 包、32 MiB，每包限制 8 MiB，视频等待阶段总上限 16 秒。**只统计编码包，不解码、不记录或回传任何手机屏幕二进制数据**；界面显示实际编码尺寸、接收帧数、关键帧数、实验耗时与字节量。

成功或失败都会关闭本轮本地媒体 socket、终止本轮 adb shell 子进程、移除仅本轮的 forward 规则并删除本轮 Android 临时 jar；不会执行 `adb disconnect`、`adb connect`、后台定时重试、IP 回退或触屏控制。端点持有对应设备锁，避免与用户手动更换路线/该设备截图交叉操作。不存在永久投屏进程或任何保存的视频文件。

返回的 `stream_received=true` 仅表示 **Android 编码器 → ADB → FNOS** 成功抵达；`continuous_frames=true` 表示至少收到两个视频帧，`web_decode_verified=false` 仍明确表示尚未完成 Web 端 H.264 解码。即便请求了原生参数，也应以结果中的 `encoded_width` 与 `encoded_height` 判断实际编码尺寸，不凭屏幕 `wm size` 推断输出能力。H.264 性能及实际帧率需真机测试；单次小样本不代表持续稳定码率或 60 FPS 能力。

现场验收先使用 baseline，确认正常后再主动触发 native。若 Docker 构建不能访问官方 GitHub Release，镜像会停止更新，保留旧部署；不应关闭 SHA 校验强行继续。

### 首次现场故障修复：两种档位均提示「scrcpy 视频流提前结束」

原因是旧版 `_connect_forwarded()` 把 **ADB forward 的本地 TCP 接受连接**误当作**Android 端 scrcpy localabstract socket 已就绪**。事实上，本地 TCP 连接可先成功，Android 进程仍在初始化，此时转发连接会立即 EOF。scrcpy v5.0.1 官方客户端针对 forward 模式会在建立临时本地 socket 后读取手机端发送的 `0x00` dummy 握手字节；未就绪时关闭该本地 socket 并短暂重试。M2 实验已采用这一机制，同一轮显式触发的实验内有总超时约束，**不运行 adb connect、不切换设备 IP，也不启动后台自动重试**。握手字节只消费一次，后续流解析直接从 64 字节设备名开始。

此外，手机端标准输出与错误输出只写入随请求关闭的临时文件；若服务器提前退出，响应会包含退出码及有限的安全故障分类（如版本不匹配、权限/屏幕捕获错误、MediaCodec 初始化异常），不回传原始 Android 日志或视频数据。新增模拟 ADB 转发「首次连接立即 EOF、第二次拿到真实握手」回归测试；还不能据此声称 FNOS 实机问题已经解决。请先更新 M2 并只点一次「视频实验 · 基础」，若仍失败，把页面显示的**完整错误提示**发回，不要提交 `.env`、Token 或 Android 全量 logcat。


## M2-00-E：HTTP + NAS IP 实时视频第一版（真机待验收）

用户采用 NAS 局域网 HTTP/IP，故不依赖必须使用安全上下文的 WebCodecs。第一版采用浏览器 Media Source Extensions (MSE) 播放 H.264 fragmented MP4，检测浏览器真实支持的 avc1 编码标识。

已连接设备点击「开始实时画面」后，浏览器与同源 WebSocket 建立连接，连接成功再通过首条认证消息传递当前页面内存中的 Token、档位和 selected_serial；不把 Token 放在 URL。服务端比对 Origin/Host、访问密钥、当前选中地址及 ADB 在线状态，同一台逻辑设备最多一个正在运行的会话。

复用固定官方 scrcpy-server v5.0.1 的仅视频 socket；服务端解析 H.264 Annex B 包，将视频通过 Debian FFmpeg 的 copy 模式仅转封装（不重新编码）为 fragmented MP4，使用 empty_moov、default_base_moof、frag_every_frame。服务端从 ftyp/moov/avcC 提取真正 avc1 编码标识，再发送初始化数据和媒体分片。浏览器使用 MediaSource、SourceBuffer 和 video 标签连续播放，控制缓存积压和陈旧缓冲区。

手动停止、关闭网页、切换连接 IP、修改分组或删除设备后，终止本轮会话并释放 socket、FFmpeg、scrcpy 子进程、仅本轮的 ADB forward 和远端临时 jar。不会自动 adb connect、不会 IP 回退、不会自行建立后台会话。首版不包含触摸、键盘、声音、录屏或自动重连。

当前 M2-00-E 只有代码/离线测试验证，尚不能声称浏览器持续画面已在 FNOS 真机通过。横竖屏变化会改变 MP4 视频轨尺寸，第一版提示停止并重新开始，后续再做不间断旋转适配；不承诺已量化的真实延迟和 60 FPS。

HTTP 本身不加密，适合你当前受信任的内网，不建议把该端口直接暴露公网；外网使用应另配 HTTPS/WSS。

现场验收：更新 M2 → 重新加载页面 → 手动连接 PJZ110 → 先选基础档点击「开始实时画面」→ 验证画面连续和手动停止 → 再试原生档。失败时只需返回页面错误文字和浏览器型号，不要发送 Token、.env 或视频数据。
### FNOS 首次实时画面故障：WebSocket 网络错误（代码修复，待现场复测）

首次用户反馈「实时视频 WebSocket 发生网络错误」。静态核对发现原镜像 `server/requirements.txt` 仅依赖基础版 `uvicorn`，遗漏 Uvicorn 进行实际 WebSocket HTTP Upgrade 所需的 `websockets` 或 `wsproto` 后端。之前的视频实验是普通 HTTP 请求，FastAPI TestClient 进程内模拟 WS 也不能证明 Docker 内的 Uvicorn 能进行真实网络握手。这是与现象一致的明确部署缺陷，但最终原因仍须以 FNOS 日志及重新部署后的复测判断。

已增加 `wsproto>=1.2,<2`，Docker Uvicorn 显式以 `--ws wsproto` 启动，遗漏依赖时启动失败而不是 HTTP 看似正常、WS 却无法升级。新增真实本地 TCP 握手测试：同源连接必须返回 `HTTP/1.1 101 Switching Protocols`，跨来源返回 403。页面细分握手失败、已连接尚未初始化和实际流中断，并提示检查 FNOS 日志。两种模式的部署脚本均需**重新构建镜像**才会安装依赖，单纯刷新浏览器无法修复老镜像。

建议复测：更新并重建 M2，重新加载页面，先用 HTTP + NAS IP 直连 EasyADB（避免未经配置的中间代理），手动连接 PJZ110，选择基础档开始实时画面。若仍失败，回传页面完整错误及 `sudo docker compose logs --tail=100 easyadb`（无代理模式加 `-f compose.no-proxy.yaml`）；只分享已脱敏日志，不分享 Token 或 `.env`。
### 播放引擎接口预留（本轮调整）

为了保持普通 HTTP + NAS IP 直接可用，当前正式测试入口**固定为 MSE**。将旧的内联播放器拆分为独立 `web/m2-player.js`，由 `EasyADBPlayers.create(kind, video, hooks)` 创建实例；播放器的基础契约是 `initialize(metadata)`、`append(chunk)`、`resume()`、`destroy()`。MSE 实例处理 MediaSource、SourceBuffer、播放追帧与缓冲清理，Web 页面的设备/鉴权/WebSocket 逻辑不负责直接操作这些对象。

`EasyADBPlayers.WebCodecsPlayer` 只提供相同接口的**显式未实现占位**，`capabilities().webcodecs.implemented` 恒为 `false`，不能选择也不能触发真实解码。未来先补 raw H.264 SPS/PPS/帧/时间戳协议，再接 `VideoDecoder` 和 Canvas，不能将当前 fMP4 分片直接交给 WebCodecs。

WebSocket 认证首条消息新增 `player: "mse"`。旧客户端省略该字段时为兼容仍按 MSE 处理；请求其他播放引擎将返回明确错误且**不会启动 ADB 或 scrcpy**。当前初始化事件明确返回 `player: "mse"`、`format: "fmp4"` 及动态 H.264 MIME。JS 文件由 `/m2-player.js` 提供并禁用缓存。首版仍以 MSE 实机效果为唯一验收目标，不声明 WebCodecs 已完成。

自动化除 Python / Shell / HTML 检查外，增加 Node 独立模块实际运行测试：验证 MSE 在 `sourceopen` 前到达视频字节时先入队、就绪后按顺序 append；验证释放/销毁及 WebCodecs 无法误启用。
### M2-00-E：手机空闲后视频间歇卡顿（时间轴和播放器修复，待真机复测）

scrcpy v5.0.1 的 `SurfaceEncoder` 使用 `MediaFormat.KEY_REPEAT_PREVIOUS_FRAME_AFTER`，默认 100,000µs；即静止时仍可能约每 100ms 输出上一帧（具体受设备编码器实现影响），**并非始终恒定输出 30fps**。原 MSE FFmpeg 命令通过 `-f h264 -r 30 -i pipe:0` 给无原始时间戳的 Annex B 输入套固定 30fps 时间轴，导致空闲时约 10fps 的视频数据被压缩为约三分之一的播放时长。MSE 播放头会频繁抵达最新缓冲区末尾而等待，用户看到间歇停顿。该代码缺陷与现场症状高度吻合，仍需 PJZ110 验证是否存在其他因素。

本轮 FFmpeg 增加 `-use_wallclock_as_timestamps 1`，采用输入到达时间作为临时近似 PTS，保留 `-c:v copy`、H.264/fMP4/MSE，不要求手机强行输出 30fps；增加 `-flush_packets 1` 减少输出端积压。原始 scrcpy 包头已包含手机侧 PTS，但 raw H.264 pipe 不传递这个元信息，将来如需精确同步/跨帧排序应换支持原始 PTS 的 muxer，当前不能将 wallclock 说成完整保真。

浏览器 `MSEPlayer` 增加 `waiting/stalled` 事件识别：静止时允许保留最后一帧，不在无新数据时频繁 seek；新片段到达且播放头仍卡在旧末尾时，移动到新近可播放范围；出现大的 PTS 间隔时按**最后一个** buffered range 的起点定位，避免跳进旧 range 与新 range 的空白区。destroy 会取消所有新增监听，无后台手机触摸、ADB 重连或独立设备保活。

回归：Python 真实 FFmpeg 间歇流测试按约 100ms 输入 12 帧并检查最后 MP4 PTS；Node 模拟 MSE 在静止、waiting、最新区间出现断层及追加新帧后的自动恢复。请按原 M2 构建脚本重建镜像并硬刷新网页，保持手机画面不操作一段时间后再在手机本机滑动/打开应用，验证浏览器是否快速更新，而不是把静止画面本身误判为冻结。WebCodecs 仍仅预留未实现接口。
### M2-00-E：空闲卡顿及重新进入约 5 秒的分阶段诊断（等待 FNOS 实测）

用户反馈空闲画面间歇性卡顿，且卡顿后重新刷新/进入有时等待约 5 秒。该耗时不能直接归因于 Android 静止帧：当前 WS 在重新建会话前执行 `adb -s selected_serial get-state`（单次最多 6 秒），旧会话退出也可能等待清理，新会话需 push/forward/scrcpy 握手/FFmpeg 首个 MP4 初始化段。**不要在未量化时把卡顿归因于某个环节，避免反复猜测 FFmpeg 参数。**

为已认证、用户明确点击开启的 WS 会话新增轻量阶段诊断。服务端只用现有媒体包到达事件和 `time.monotonic()` 记录阶段、会话时长、收到的 H.264 媒体包数及末次到达距今、FFmpeg 输出次数及末次距今、MP4 初始化段就绪时间；首条 `starting` 携带 ADB 在线检查耗时。既不额外执行 ADB 指令，不采集图像、不泄露 Token，也不保持无人在线的后台任务。浏览器用同一个 WS 的诊断消息每约 1 秒展示网络收包距今、`requestVideoFrameCallback` 实际渲染数量/距今（支持时）、当前 buffered 与播放位置的间隔、readyState。`beforeunload`/手动停止继续终止会话，cancel 渲染回调。

复测操作：手动连接选定 PJZ110，基础档开始投屏，截图记录视频刚打开时的 ADB 检查耗时与阶段；手机保持亮屏静止 2–3 分钟，卡顿时记录一整行「投屏诊断」，随后仅在手机**本机**滑动并再记录诊断。如果手机编码包距今持续增长 → 手机/scrcpy 输入需要进一步排查；手机到包更新但 FNOS MP4 输出不更新 → 转封装/时间戳需排查；MP4 输出更新但网页收包不更新 → WS 队列/网络需排查；网页收包更新但实际渲染不更新 → MSE 缓冲/解码需排查。此分支仅做诊断，不承诺已修复现场未知根因。
### M2-00-E：FNOS 收包正常但 MSE 停止渲染（针对性修复，待 PJZ110 复测）

用户卡住时的真实诊断：约 398.9 秒会话，ADB 检查 54ms，手机 H.264 编码包 8864/距今 0.0s，FNOS MP4 输出 9044/距今 0.0s，浏览器二进制收包距今 0.0s，但 `requestVideoFrameCallback` 实际渲染距今 3.3s；`video.buffered.length===0`，video readyState=2。**当前瓶颈在浏览器收包之后**，并不能据此判定 Android 停止编码，也不能单凭 `video.buffered` 空值断定 SourceBuffer 的内部状态。

审查发现 MSE 播放器 `_pump()` 旧实现一旦 `queue.length > 0` 就 `appendBuffer` 后立即 `return`，旧版本的追赶实时位置和 `remove` 只在**队列完全排空**时运行，持续不断追加的真实视频会话可能始终不触发缓冲维护；长期运行后极易落后播放头、遭遇浏览器内部驱逐后仍未追上最新范围。这是确定的代码逻辑缺陷，但仍需实际浏览器验收确认是否为现场唯一原因。

本轮将 `_maintainLivePosition()` 放到每次异步 `SourceBuffer.updateend` 后、处理后续 queued append 之前；仅在 remove 更新完成后继续追加，保留错误处理和浏览器手动停止。缓冲清理保留窗口由 8s 扩大到 16s、触发阈值 24s，因为固定 scrcpy v5.0.1 `SurfaceEncoder` 默认 I 帧间隔约 10s，过早删除 GOP 起始关键帧可导致后续画面无法正常解码。追帧逻辑仍只在已有新媒体或明显落后时生效，没有后台模拟触摸、自动重启、额外 ADB 探测。

增量诊断加入播放器自身 `SourceBuffer` 范围数及最新范围起止、MediaSource 状态、SourceBuffer updating、待写队列、append/update 次数及最近 update 距今、播放位置、seeking 与 HTMLMediaElement error code。现有 `video.buffered` 仍单独显示，便于判定是 SourceBuffer 本身无解码范围，还是 video 可播放范围/播放头不匹配。Node 模拟真实异步 `appendBuffer`：在第二块仍排队时，第一块 updateend 必须执行追帧；异步 remove 必须完成才继续追加，并保留 16s 视频时间轴。

验收：更新构建并硬刷新，基础档连续运行 7–10 分钟，在卡顿时保留整个诊断截图（尤其是 `MSE` 字段）；如果 SourceBuffer 持续有新 range 但不渲染，进一步关注关键帧、时间戳及浏览器 seek；若 SB 区间始终为 0，而 append/update 次数仍持续增长，需要进一步检查真实 MP4 box/时间戳结构，不要再盲目调整 Android 帧率。
### M2-00-E：首轮低延迟优化（按完整 fMP4 帧传输，待 FNOS 验收）

真机新诊断：会话约 7.2 秒时，手机编码包 175、FNOS FFmpeg 管道读取 344、浏览器 SourceBuffer `append/update` 343/342、渲染 147 帧；MSE `open`、SB 1 个区间、待追加队列 0、buffered 前沿余量约 0.20s、readyState=4 且 error 无。这意味着先前无法渲染的问题已有改善，但**0.20s 仅为缓冲前沿余量，不是完整手机→浏览器延迟**；不能从会话时间减去 currentTime 来直接估计端到端时延，因为会话还包含启动时间。

优化聚焦重复处理开销，不改码率或增加主动缓存：原 `os.read(32768)` 为任意操作系统管道字节边界，同一帧的 moof 和 mdat 经常被拆成多个 WebSocket 消息/浏览器 append。现新增有长度上限的 `Fmp4FragmentAssembler` 逐盒解析并在**当前 moof + mdat 完整时立即**发送，一帧可单次浏览器 append；允许合法可选 `styp/free/sidx/emsg/prft` 前缀与结束 `mfra`，对异常 MP4 尺寸或孤立媒体盒失败关闭，不延迟到下一帧。服务端新增 `media_fragments` 会话诊断，区分 FFmpeg 原始管道读取数和完整帧发送数。

播放器避免在每次 SourceBuffer `updateend` 都无条件重复调用 `video.play()`；只在需要恢复播放且没有悬而未决的 play 请求时调用。不降低现有 0.15s 追帧目标，以免 0.20s 左右的稳定缓冲直接被压成卡顿。诊断另显示 `init_ready_ms`，将 MP4 首次初始化的启动耗时与运行中 video 缓冲余量区分。

本轮新增真实 FFmpeg 12 帧测试：把 MP4 媒体数据按 37 字节任意切块喂入 reassembler，验证按 moof+mdat 恢复为 12 个完整分片，保留原字节顺序；合成测试覆盖字节级拆分、可选盒以及损坏盒。Node 回归验证多次 SourceBuffer 更新不会反复调用 video.play。HTTP + MSE、用户手动 selected_serial、WebCodecs 未实现接口不变。期望浏览器 append 数明显接近完整帧数，但**绝不预先宣称毫秒级改善**；FNOS 真机需对比相同档位、相同动态画面连续 7–10 分钟的实际响应。

### M2-04-A：统一停止与可验证的资源释放（代码完成，待 CI/FNOS 验收）

沿用 M2-01 的一个 LiveVideo / 一个随机 session_id / 一个认证 WS，会话级的 stop_event 同时阻止后续触摸、文本和导航注入。用户直接停止投屏时，若本轮手指仍为 DOWN/MOVE，先在同一个控制 Socket 尝试发送 CANCEL（pressure=0），再关闭控制 socket、视频 socket，并终止本轮 FFmpeg/scrcpy；无后台重连、无 adb disconnect，也不再开启第二套控制会话。重复停止不会再次发送 CANCEL；即使控制 socket 的 CANCEL/close 报错，也继续尝试其余会话资源清理。

区分 `finished`（worker 终止）与 `cleanup_complete`（本轮拥有的资源经清理流程确认已释放）：只有后者成立，才从 LiveRegistry 释放设备槽，并允许下一次手动开始；未确认时返回错误而不发送 `ended(cleanup_complete:true)`，设备槽继续占用以避免并发碰撞。资源清理按已实际创建的内容执行：只有成功 push 才尝试远端 jar 删除，只有创建 forward 后才尝试移除该端口；清理失败采取 fail-closed。按用户后续决定，原计划的 M2-04-F 显式恢复功能已取消，不宣称当前存在该恢复入口。启动线程失败会回滚新 reserve，避免永远卡在尚未启动的 candidate。未改变 MSE/FFmpeg 视频参数、scrcpy 固定版本、连接地址选择或自动行为。

### M2-04-B：浏览器异常关闭与失联处理（代码完成，待 CI/FNOS 验收）

此前接收到 `WebSocketDisconnect` 时能释放本轮投屏，但半开 TCP/浏览器冻结可能长时间没有断开事件，媒体发送也可能被网络写入阻塞。现在在**用户主动启动的本轮会话内**增加有限期浏览器存活检查：服务端沿用现有约每秒一次 `diagnostic` 消息，网页收到后通过同一个认证 WS 返回 `{type:"heartbeat",session_id}`，不另外启动 JS 定时器、不运行 ADB 探测、也不向手机注入任何触摸。心跳只接受当前 Session ID、字段严格为 type/session_id 且对应数据库中手动选择并已连接的 serial；旧会话/跨设备/异常格式按现有 fail-closed 规则终止本轮 WS。未经有效认证不能创建 watchdog。

服务端初始宽限期及连续存活期限均为 **45 秒**，每 **2 秒**检查一次，使用单调时钟；**只在投屏 WS 正在运行时**存在，停止/异常结束即取消。浏览器持续处理诊断即可续期，不依赖用户是否触摸手机，也不自动连接、重连或 IP 回退。若浏览器不再处理网络消息、TCP 保持半开而服务端收不到确认，则停止本轮 worker，释放控制/视频/专用 ADB 资源；只有 `cleanup_complete=true` 才释放当前设备槽。网络发送（包括会话启动、诊断、初始化、视频媒体及终止确认）使用 **10 秒超时**，避免本轮 WS 输出永久卡死；超时同样进入现有 finally 清理路径，**不会静默恢复旧会话或自动新建会话**。

浏览器另外对 `pagehide` 和显式 `offline` 事件立即调用既有 `stopLive()`，阻止触摸/键盘继续注入、销毁 MSE 并尝试停止关闭旧 WS；由于网络可能已断，后端仍由独立存活宽限来收尾。现有 `beforeunload` 保留，所有动作幂等；页面恢复网络后仍须用户手动重新开始，不将隐藏标签或手机静止本身判定为断线。长期冻结页面若无法处理诊断长达 45 秒会被认为已失联，这是刻意的孤儿会话安全权衡；FNOS 需对后台标签、浏览器节流及真实 Wi-Fi 断线进行实测。

新增 `tests/test_m2_disconnect.py` 覆盖不回心跳的半开会话超时、静止页面只回复诊断即可继续存活、旧 Session 心跳被拒绝、媒体 WS 写入超时后的资源释放、网页没有独立周期心跳计时器。自动化代码已提交，不等同于 CI/FNOS 实机验收。M2-04-C 另有实现记录；D/E/F/G 后续功能及独立验收任务已取消。

### M2-04-C：ADB 设备异常断开与状态同步（代码完成，待 CI/FNOS 验收）

复用当前 LiveVideo 视频/控制 Socket、scrcpy 子进程与 M2-04-A 的统一退出，不引入周期性 `adb get-state`、`adb connect`、备用 IP 回退或其它后台设备轮询。原本视频 feeder 在 scrcpy Socket EOF / 读写异常时只向事件队列提交错误、等待转封装进程随后退出；现在提交错误后立即置位本轮 stop_event，促使持有线程进入统一清理。读视频包及主转封装循环还检查**本轮已创建的 ADB/scrcpy Shell 子进程**是否退出，即使已建立的 TCP Socket 没及时 EOF，也可在下一次媒体读取/主循环中识别异常。此处 `poll()` 是检查当前本地子进程，不是额外 ADB 指令；正常手机静止不构成断线证据，不设基于编码包空闲的自动关闭阈值。

媒体异常或控制 Socket 写入异常发生后，服务器**事件驱动地仅对该次异常执行一次**已选 `selected_serial` 的 `adb -s ... get-state`：若仍在线，保留原始编码/控制错误，不误改 M1 的设备连接状态；若明确不在线，在原设备锁内重新校验当前持久化路线与管理器实际连接地址后，才把其缓存状态标记为 disconnected。若检查本身超时或无法确认，不擅自报告“已确认掉线”。来自旧会话的迟到结果绝不能覆盖当前已切换的其它设备地址。返回给网页的错误可带 `code=adb_disconnected`；网页只读取一次已有 `GET /api/devices` 的缓存快照刷新显示，禁止在失联后自动启动新会话/连接手机。无任何 ADB 状态轮询在无人在线后继续执行。

底层拥有的控制/视频 Socket、FFmpeg、scrcpy Shell、ADB 本地 forward 与手机端临时文件仍采用 M2-04-A 的逐项清理与 `cleanup_complete` 规则。如果设备离线导致远端临时文件无法确认删除，**不把清理失败伪装为成功**，保持该设备槽占用并报告清理未确认（原定 M2-04-F 恢复入口已取消，后续不自行解除安全限制）；不会悄悄启动第二路会话。正常手动停止、浏览器失联与其它非媒体故障不触发本次额外 ADB 检查；ADB 掉线后恢复也必须由用户手动连接并重新启动。

新增 `tests/test_m2_adb_disconnect.py`：真实 socketpair EOF 和主动 stop 的区别、已存在本地子进程退出时终止半开媒体读取、在线编码器异常不误报断线、明确离线时只清空当前地址状态、未知状态不武断标记，以及实际 WS 异常事件每轮仅触发一次确认并避免自动重连。代码提交和静态检查不等于 CI/FNOS 真机验收。根据随后确定的开发范围，M2-04-D/E/F/G 全部停止后续开发，直接进入 M2-05。

### M2-05-B/C：实际播放诊断、画质表现对照、资源成本及适配建议（代码完成，待 CI/FNOS 验收）

`web/m2-metrics.js` 基于本轮已存在的每秒诊断事件采样浏览器 `getVideoPlaybackQuality()`（优先）、原有 `requestVideoFrameCallback()` 计数（兼容降级），计算窗口内**实际呈现帧率**及丢帧比例；掉帧从 totalVideoFrames 中扣除一次，不重复计算。同步展示 MSE 播放缓冲余量、最近渲染帧距今、浏览器实际收到的视频载荷 Mbps / 累计流量、待追加媒体队列。静止 Android 画面的低 FPS / 低码率**不单独意味着故障**。本轮采样仅在已打开 WS 的 `diagnostic` 消息到达时执行，无新 JS 定时器、无后台设备探测；结束后将最多最近 **8 次本页会话**的均值及峰值放在内存中，刷新页面即清空，不收集或储存视频内容。

### M2-06 使用反馈后的集中修复：多路卡顿与第二路控制（待 FNOS 验收）

针对“多路投屏很卡、开启第一台后第二台远控无法开启”的反馈，检查发现多设备卡片把“可开启控制”错误关联到该卡 HTML5 Video 的 `playing` 事件，并且早期控制失败的 `touch_error` 没有解除 pending，可能造成第二个按钮长期无法操作。现在独立区分**本轮 scrcpy 控制通道就绪**与**浏览器已开始呈现首帧**：收到有效 `init` 并建立该卡控制器后即可启用远控，即使该画面还在等待解码；如果尚未获得视频的实际 `videoWidth/videoHeight`，文字和导航仍可操作，鼠标坐标映射待画面真正解码后才生效。控制请求被拒绝或早期报错会释放本卡 pending，不影响其他设备。所有发送仍限当前卡 WS 和 Session ID，默认只观看。

多设备同屏为**每台设备**分别提供画质选择，默认省流（每路最大边 960 / 3 Mbps / 24 FPS），也可分别选基础、原生或本设备自定义；不再有共用“沿用上方设置”选项，不修改服务端旧档位，任何画质只在该设备新一轮手动启动时应用，不自动降档。同屏启动从一次用户点击选中的设备队列中，等待上一设备经认证 WS 返回有效 `init`（scrcpy/FFmpeg 已完成初始化）才打开下一路；早期启动失败时继续处理队列，主动停止全部或页面退出时立即取消未启动项。无延迟定时器、无无人值守重连，避免几台手机的 scrcpy jar 推送、FFmpeg 和 MSE 初始化同时冲击 NAS。

多设备卡片启用 `lowOverhead` MSE 追加：只在 SourceBuffer 繁忙、已有**完整 fMP4 媒体分片**在本卡队列中等待时，将最多 4 个、合计不超过 256 KiB 的分片合并成一次 appendBuffer；只有一个分片时立即追加，**不等待下一帧**，不改变 H.264 或 FFmpeg 时间戳、对齐和单设备默认播放参数。此举降低多路 SourceBuffer append/updateend 负载，但是否足以解决 FNOS 实际卡顿仍需真实 CPU/GPU/网络数据确认。

回归覆盖：第二台在没有 `playing` 事件时仍能启用控制、`touch_error` 后可重试、每卡心跳和控制只属于自己的 Session ID、两个画面依次启动、四路上限、某一路失败不停止其余路、停止全部取消排队中的未启动连接，以及 MSE 多分片合并与静止画面不等待下一帧。历史阶段曾使用 workflow_dispatch 手动触发；当前按用户最新决定已恢复开发分支 push 自动运行 GitHub Actions；本轮前端契约模拟已通过，CI/FNOS 真机仍待执行。此前 M2-04-D/E/F/G 仍按用户要求取消。

### M2-06：投屏期间增量设备管理与追加同屏（代码完成，待 FNOS 验收）

此前前端把 `hasActive()` 用作整页操作锁：任一设备投屏就阻止**其它设备**的连接与线路切换、禁止新增分组，`start()` 发现任何已有卡片也直接返回，导致用户无法先投屏 A/B，再添加并手动连接 C、勾选 C 点击开始追加。后端 `POST /api/devices` 原本没有全局直播锁；真正阻碍新设备加入的是前端 `runConnect` 的不分设备检查。

现改为**按设备区分冲突**。投屏期间允许新增设备、新增分组、连接或切换**尚未占用直播槽**的其他设备；对正运行、启动中或待服务端清理完成的目标设备，禁止修改其线路、重新连接、编辑/删除，避免直播与所选 ADB serial 不一致。若分组内有直播设备，该**现有分组**修改/删除仍受限（后台更改分组缓存可能终止成员会话）；创建其它新分组不受限。全设备刷新因其可能同时触及直播设备仍暂不放开。单个目标的显式能力预检和视频实验不再被其它设备的直播状态全局锁死，已运行的同一设备仍不能另做实验。

「开始投屏」现在根据当前 `selected` 与 `cards` 的设备 ID 差集，只为**尚未建流且已手动连接**的新勾选设备执行启动队列；有直播卡且有新增设备时按钮显示「追加投屏（待新增 N / 剩余 M 台）」，没有新增设备时不可点击。现有会话不会停止、重建、替换 MSE 播放器、改变画质或远控状态。单设备处于 stopping/等待 cleanup 时仍占名额，只有已确认结束后才可再次创建相同设备流。原来一次用户点击对应的多路依序启动规则保留：下一台要等前一台 `init` 后再启动，无自动连线和后台重试；服务端 `LiveRegistry` 仍为同时最多四台，一台只允许一个会话。停止全部依旧结束当前所有设备，并取消尚未开启的队列，保留这次明确勾选集合供再次手动开始；单独停止一台且其它设备仍运行时，该台会从待追加勾选中移除，避免下一次点「追加投屏」意外重启它，重新投屏须主动再次勾选。追加操作不会触发全停。

新增/强化回归：A 运行中页面加载新增 F，并选择 F 单独追加；验证 A 的 Card / MSE / WS / 控制状态对象完全相同；继续补足四路、第五路禁用、单路 `ended(cleanup_complete=true)` 后释放一个槽再加入另一台，最后全停确保没有旧 DOM；服务端以假会话占用 A 的同时，通过认证接口创建 B 和新分组，确保 A 不被 stop。CI 通过仅代表代码验证，FNOS 真机仍需现场验收。

### M2-06：设备管理逐台实时画面状态及开关（代码完成，待 CI/FNOS 验收）

设备管理中的每台横向设备行在画质与检测区下方新增**独立「实时画面」状态与操作按钮**，状态只描述本网页拥有的直播会话（未开启 / 排队中 / 启动中 / 等待画面 / 播放中 / 停止中·等待清理 / 已停止 / 异常结束等），绝不将数据库的 ADB 连接状态冒充为视频正在播放；不增加服务器轮询或自动连接。用户在某台已明确手动连接的设备行点击「开启此设备画面」，只为该设备创建一次独立的 WS、MSE 与控制会话，即便同页另有设备已勾选但未开启，也**不**附带启动它们；开启后自动将该台纳入页面勾选集合，保留已有批量「开始/追加投屏」及「停止全部」功能。

已运行设备行显示「关闭此设备画面」，只向该台当前会话发停止命令并等待服务器清理；停止中按钮禁止重复操作，同一设备绝不重复建流。队列中尚未开始的设备可单独取消，不能因此启动额外手机；并发仍最多四台。当前行的开启/关闭直接更新同页视频网格，其它设备的会话、远控与播放器不受影响。状态来自该卡原有 WS 启动、初始化、播放、停止/完成事件；终止后 UI 保留「已停止」或异常信息，用户可明确手动重新启动。本页刷新后这些临时直播状态重置，跨浏览器会话接管仍不支持。

增强 Node 契约与 Python 静态测试：验证每设备状态切换、单台启动不夹带其它已勾选设备、只停 A 而 B 不停、等待清理期间不得重开、完成后能重开、排队项取消不建立 WS、四路限制及原批量操作不回归。静止画面偶发卡顿按此前决定暂缓，**本项不修改 scrcpy 编码或 MSE 播放时序**。

### M2-06：简化设备画质设置与隐藏实验入口（代码完成，待 CI/FNOS 验收）

按最新设备管理界面要求，暂时隐藏每台设备行中的「能力预检」「视频实验·基础」「视频实验·原生」及「检测记录」展示；仅隐藏前端入口，不删除原有后端检测 API，不自动进行检测。实时画面卡片内已存在的本轮诊断日志仍保留。

原来只能选择“省流/基础/原生/自定义”档位、选中自定义时才出现额外字段，现改为**每台设备直接提供三个并列且完全独立的下拉设置**：

- 分辨率最大边：960 / 1280 / 1600 / 不限制（`max_size=0`）；
- 目标视频码率：2 / **3** / 4 / 8 / 12 / 16 / **18 / 20 Mbps**；
- 最高帧率：15 / 24 / 30 / **45 / 55 / 60 FPS**。

默认仍显示并实际请求 `960 / 3 Mbps / 24 FPS`。 已扩展的 18/20 Mbps 和 45/55/60 FPS 均走同一份前后端参数白名单，旧非法 60 FPS 测例同步修正为越界 61 FPS。这里的值是 **scrcpy 编码器请求的码率目标与最高帧率上限**，实际输出取决于手机编码器、屏幕内容变化与设备负载，并不承诺恒定 60 FPS 或实际占满 20 Mbps。前端为这些组合统一生成 `profile=custom` 以及三个数字字段，服务端 `CUSTOM_CHOICES` 同步增加 3 Mbps 严格白名单，所以默认设置也可通过完整的自定义校验。旧 `economy`、`baseline`、`native` 服务端预设及原视频实验接口继续兼容，但设备行不再展示一个额外的画质档位选择器。运行期间冻结该台设备已选值，改变三个下拉只能作用于**该设备下一轮明确开启**的会话，不热切换、不重建现有流，不影响其他设备；刷新网页后仍使用省流默认值，不引入数据库持久化。

新增 Node 回归覆盖 A/B 分别设定三个独立字段、默认 3 Mbps 的 WS 请求、运行中禁止热配置、检测功能隐藏但原明确调用逻辑保留；Python 测试覆盖 3 Mbps 白名单及非法参数仍在调用任何 ADB 前被拒绝。保持上轮约定的静止屏幕卡顿暂缓，不动 MSE / FFmpeg / scrcpy 视频链路。

### M2-06：批量设备管理、直点 IP 与默认低延迟（代码完成，待 CI/FNOS 验收）

设备管理新增**独立于实时投屏勾选的批量管理勾选框**、全选/取消全选、已选数量、「批量连接」和「批量删除」。全选不受同屏四路上限影响；已有流/排队或清理中的设备可以显示为已选，但真正执行时要明确跳过，不得停止现有会话。「批量连接」按设备列表顺序逐台显式调用原有已授权的 `POST /api/devices/{id}/connect`，只连接各设备已经选定的线路，不更换组网/内网 IP、不自动探测其它地址、不创建视频会话，逐台收集成功或失败；操作中锁定编辑/其它批量操作，结束后刷新一次设备状态。批量删除必须二次确认，展示待删除名单及跳过的运行中设备数量；确认后逐台调用原有 `DELETE /api/devices/{id}`，每台失败不会停止后续删除，保留失败设备勾选，并报告实际成功/失败/跳过数量；不会主动清除手机端配对授权。改变访问密钥时清空管理选择，刷新列表时剔除已被删除的设备 ID。

每行原先的组网/内网 IP 文本 + 「✓ 当前选择 / ⇄ 切换」组合，简化为**IP 本身就是可点击的线路按钮**，当前地址通过选中底色/`aria-pressed` 表示且不再显示冗余文字；点击非当前 IP 只保存路由偏好，仍需显式点击「连接」，不新增自动 ADB、线路回退或后台探测。运行中的设备仍不能切换自己的地址。设备标题改为「设备名称（设备型号）」；无型号时只显示设备名称，下方保留 Android 版本信息，但不再重复显示设备型号。

各设备的「低延迟播放实验（仅浏览器追帧，不改变手机编码）」由默认关闭调整为**默认勾选**，只影响新启动的该设备当前网页播放器；仍可对每台设备独立取消、运行中不热切换，播放结束后速度恢复规则不变。该选项仅处理已有浏览器缓存积压，不宣称解决手机编码器或 Android 静止画面恢复卡顿；按此前决定，不额外更改 scrcpy、FFmpeg、MSE 播放时序。新增/更新前端契约与 Python 静态检查；本批单次提交，由 Push 自动 Runner 检验后，再进行 FNOS 真机验收。

### M2-06：小米澎湃 OS 3 远控权限与延迟排查（代码完成，待 FNOS 真机确认）

用户反馈 ColorOS 画面与远控基本可用，但澎湃 OS 3 可投屏、无法远控且视频延迟明显。此处不能把成功建立/写入 scrcpy control Socket 等同 Android 已接受注入。官方 scrcpy FAQ 明确指出部分小米设备还需在开发者选项中单独开启 **USB 调试（安全设置）**（不同于普通 USB 调试），完成授权并重启：https://github.com/Genymobile/scrcpy/blob/master/FAQ.md 。操作由用户在手机上完成，EasyADB 不自动改系统安全设置、不请求 root、不绕过权限。首先对比同一台澎湃设备的固定导航「主页」与视频上单指点击：两者均无反应优先排查系统模拟输入授权；仅触摸无反应再追查实际分辨率/黑边/坐标映射。

新增 `server/m2_control_diag.py` 对本轮 scrcpy ADB shell 的私有 stdout 作**被动、白名单**权限拒绝分类。仅当用户已明确发出触摸或按键/文字指令，已有每秒诊断消息才用 `os.pread` 读取本轮持有的临时进程输出，查找 `INJECT_EVENTS`、注入相关 SecurityException 等；只将固定值 `control_warning=android_input_permission` 回传，不上传原始日志、Token 或文字输入，不另发 ADB 指令、不持续 logcat。若系统输出没有记录该错误，则不伪称已确认权限正常。页面出现明确拒绝时仅关闭该设备已开启的控制通道并给出安全设置提示，其他画面/设备继续运行；`control_enabled` 文案明确表示 **Socket 已开启，并非手机已实际接收输入**。

对高延迟提供逐设备、默认关闭的「低延迟播放实验」复选框，本轮开始时冻结配置，不修改 scrcpy 画质白名单或 FFmpeg 原视频链路。仅当浏览器 MSE 当前可播放缓冲前沿领先播放点 0.60–2.50 秒时，将该设备视频以 1.15x 临时追帧；接近前沿立即恢复 1x，终止销毁也恢复 1x。不在无新帧的静止屏幕上反复寻址、不会自动 ADB 重连或为了加速而丢弃关键帧。未勾选的 ColorOS 等设备维持旧策略。此举只能改善**浏览器侧已积累的缓冲延迟**；手机编码、网络拥塞和 FFmpeg 时间戳导致的真实端到端延迟不能由它直接解决。请现场对比相同动态画面、相同省流档，收集本路诊断中的 phone_packets/phone_idle_ms、mux_chunks/mux_idle_ms、MSE 当前时间/最新 range、播放倍率、浏览器实际 FPS/帧距今与 CPU/RSS，再决定下一步是否需要调整编码器或视频管线。

新增 `tests/test_m2_control_diag.py` 及 Node 契约测试，覆盖错误分类不泄露原始日志、无输入前不检测、单设备权限拒绝时其它设备不受影响、低延迟 opt-in 与停播恢复正常倍率。GitHub Actions 已恢复开发分支 push 自动触发；本批完整代码和文档集中提交一次，FNOS 真机结果须单独确认。

## 后续技术路线（M2-07 及之后）


优先使用 scrcpy 官方项目发布的**同版本** client/server 作为技术参考/固定协议；其开发文档声明 client 与 server 通过视频、音频、控制等不同 socket 通信，视频 H.264 默认编码，协议属于内部实现、会随版本变化。M2 不将“任意 scrcpy-server 二进制 + 自写客户端”视为兼容。

参考：
- https://github.com/Genymobile/scrcpy
- https://github.com/Genymobile/scrcpy/blob/master/doc/develop.md
- https://github.com/Genymobile/scrcpy/blob/master/LICENSE

初步实验路径：固定完整版本和下载校验 → 在现有手动选中且已连接的 ADB serial 上使用会话专属隧道启动 server → 读取并解析对应版本视频元数据、帧头、编码格式 → 经认证的服务端会话转发 → 浏览器 WebCodecs H.264 解码与兼容性检查。若目标浏览器不支持所需解码能力，应明确提示，而不是错误地把截图定时轮播称为“实时视频”。控制通道须与同一个会话绑定，不能接受任意设备串号或任意 ADB shell 命令。使用官方源、审查 Apache-2.0 许可告知及分发义务；未固定版本/校验前不在 Dockerfile 自动下载或执行 scrcpy server。

## 必须继承的 M1 规则

- 只用 SQLite 中持久保存的 `selected_route` 和对应 `selected_serial`；不得自动优先内网、回退组网或定时重连。
- 会话只由已认证用户明确启动，选择变更后停止原会话；截图只使用所选设备的 serial。
- 只在会话确实运行期间允许用于检测**浏览器会话**的心跳；无人在线时不能残留设备控制进程/端口转发。容器重启后不得自行重建旧会话。
- 仅支持一个正在使用的网页客户端；保留当前单设备会话保护。M2-06 如实施多设备同屏，也仅在同一客户端页面内进行，不开发多浏览器并发或控制权抢占。

## 首次从 M1 切到 M2 的 FNOS 操作

**不能只执行旧 M1 目录里的原部署脚本**：旧脚本会把工作区切回 M1。先由原 Git 登录用户（不要加 sudo）取得并切换 M2：

```sh
cd /vol3/1000/software/EasyADB
git status --short
git fetch origin
git switch feat/m2-web-control 2>/dev/null || git switch --track origin/feat/m2-web-control
git pull --ff-only origin feat/m2-web-control
sudo sh scripts/build-with-mihomo.sh
```

如 FNOS 环境本身由 OpenWrt 处理外网，最后一行可替换为：

```sh
sudo sh scripts/build-with-mihomo.sh --no-proxy
```

之后两种命令会调用 `scripts/update-m2.sh`，仅自动更新 `feat/m2-web-control`，保留 `--no-proxy` 参数；遇到本地脏文件或分支不能快进时停止，不重置用户代码和数据。
