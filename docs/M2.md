## M2-00-B 本次实现内容

用户从 M1 设备列表里**手动连接**当前已选的组网 IP 或内网 IP 后，点击「M2 能力预检」。这个操作：

1. 使用现有 `X-EasyADB-Token` 鉴权与按设备 ID 的互斥锁；
2. 确认当前选择的 `selected_serial` 已由本会话的 M1 管理器记录为已连接，并显式执行一次 `adb get-state`；
3. 只读执行 `getprop ro.build.version.sdk`、`ro.product.cpu.abi`、`ro.product.model` 和 `wm size`，返回基本设备信息；
4. `stream_verified=false` 明确表示**尚未证明设备编码器、浏览器解码或 scrcpy 协议可工作**。

不会后台定时检查、自动连接、自动换地址、重试配对、`adb push`、创建端口转发、运行手机端进程或修改设备数据库。没连接时返回 HTTP 409。前端以文字形式展示结果，切换设备或地址后清空旧结果。

## M2-00-C/D 视频链路实验（本次实现，真机待测）

scrcpy 来源：[官方 v5.0.1 发布页](https://github.com/Genymobile/scrcpy/releases/tag/v5.0.1)，固定文件 `scrcpy-server-v5.0.1`，GitHub 官方发布资产 SHA-256：

```text
764eb6f79811d5211fe9df341120882ba9994c7a61b897d7bf3fb662e53bc536
```

构建镜像时从官方地址下载服务器文件并执行 `sha256sum -c`，不匹配即阻止构建；同版本 `LICENSE` 一同放进镜像 `/opt/easyadb/scrcpy/`（Apache-2.0）。**本次固定的协议解析仅适用于 v5.0.1**，未来升级必须连协议解析和测试一起复核，不会执行“latest”版本的动态下载。

在已明确手动连接的当前选择设备上点击「视频实验 · 基础」或「视频实验 · 原生」，调用需认证的 `POST /api/devices/{id}/m2/video-probe`，请求字段 `{"profile":"baseline"}` 或 `{"profile":"native"}`：

| 档位 | max_size | 目标码率 | max_fps | 降尺寸回退 |
|---|---:|---:|---:|---|
| baseline（基础） | 最大边 1600 | 8 Mbps | 30 | 关闭 |
| native（原生参数） | 0（不限制尺寸） | 16 Mbps | 30 | 关闭 |

实验由用户主动发起。后端仅对已保存 `selected_serial` 做一次 `get-state`，使用每次随机的 scrcpy SCID / Android 临时 jar 路径，通过 `adb -s <当前地址> forward tcp:0 localabstract:scrcpy_<SCID>` 获得宿主机回环端口，再以 `video=true audio=false control=false tunnel_forward=true` 启动固定版本服务器。先收发 dummy handshake、64 字节设备名、4 字节 codec 标识、12 字节会话尺寸头，再按 scrcpy v5.0.1 内部帧协议解析 H.264 config/media/key frame 等元数据，最多读取 48 包、32 MiB，每包限制 8 MiB，视频等待阶段总上限 16 秒。**只统计编码包，不解码、不记录或回传任何手机屏幕二进制数据**；界面显示实际编码尺寸、接收帧数、关键帧数、实验耗时与字节量。

成功或失败都会关闭本轮本地媒体 socket、终止本轮 adb shell 子进程、移除仅本轮的 forward 规则并删除本轮 Android 临时 jar；不会执行 `adb disconnect`、`adb connect`、后台定时重试、IP 回退或触屏控制。端点持有对应设备锁，避免与用户手动更换路线/该设备截图交叉操作。不存在永久投屏进程或任何保存的视频文件。

返回的 `stream_received=true` 仅表示 **Android 编码器 → ADB → FNOS** 成功抵达；`continuous_frames=true` 表示至少收到两个视频帧，`web_decode_verified=false` 仍明确表示尚未完成 Web 端 H.264 解码。即便请求了原生参数，也应以结果中的 `encoded_width` 与 `encoded_height` 判断实际编码尺寸，不凭屏幕 `wm size` 推断输出能力。H.264 性能及实际帧率需真机测试；单次小样本不代表持续稳定码率或 60 FPS 能力。

现场验收先使用 baseline，确认正常后再主动触发 native。若 Docker 构建不能访问官方 GitHub Release，镜像会停止更新，保留旧部署；不应关闭 SHA 校验强行继续。

### 首次现场故障修复：两种档位均提示「scrcpy 视频流提前结束」

原因是旧版 `_connect_forwarded()` 把 **ADB forward 的本地 TCP 接受连接**误当作**Android 端 scrcpy localabstract socket 已就绪**。事实上，本地 TCP 连接可先成功，Android 进程仍在初始化，此时转发连接会立即 EOF。scrcpy v5.0.1 官方客户端针对 forward 模式会在建立临时本地 socket 后读取手机端发送的 `0x00` dummy 握手字节；未就绪时关闭该本地 socket 并短暂重试。M2 实验已采用这一机制，同一轮显式触发的实验内有总超时约束，**不运行 adb connect、不切换设备 IP，也不启动后台自动重试**。握手字节只消费一次，后续流解析直接从 64 字节设备名开始。

此外，手机端标准输出与错误输出只写入随请求关闭的临时文件；若服务器提前退出，响应会包含退出码及有限的安全故障分类（如版本不匹配、权限/屏幕捕获错误、MediaCodec 初始化异常），不回传原始 Android 日志或视频数据。新增模拟 ADB 转发「首次连接立即 EOF、第二次拿到真实握手」回归测试；还不能据此声称 FNOS 实机问题已经解决。请先更新 M2 并只点一次「视频实验 · 基础」，若仍失败，把页面显示的**完整错误提示**发回，不要提交 `.env`、Token 或 Android 全量 logcat。


## M2-00-E：HTTP + NAS IP 实时视频第一版（真机待验收）

用户采用 NAS 局域网 HTTP/IP，故不依赖必须使用安全上下文的 WebCodecs。第一版采用浏览器 Media Source Extensions (MSE) 播放 H.264 fragmented MP4，检测浏览器真实支持的 avc1 编码标识。

已连接设备点击「开始实时画面」后，浏览器与同源 WebSocket 建立连接，连接成功再通过首条认证消息传递当前页面内存中的 Token、档位和 selected_serial；不把 Token 放在 URL。服务端比对 Origin/Host、访问密钥、当前选中地址及 ADB 在线状态，同一台逻辑设备最多一个正在运行的会话。

复用固定官方 scrcpy-server v5.0.1 的仅视频 socket；服务端解析 H.264 Annex B 包，将视频通过 Debian FFmpeg 的 copy 模式仅转封装（不重新编码）为 fragmented MP4，使用 empty_moov、default_base_moof、frag_every_frame。服务端从 ftyp/moov/avcC 提取真正 avc1 编码标识，再发送初始化数据和媒体分片。浏览器使用 MediaSource、SourceBuffer 和 video 标签连续播放，控制缓存积压和陈旧缓冲区。

手动停止、关闭网页、切换连接 IP、修改分组或删除设备后，终止本轮会话并释放 socket、FFmpeg、scrcpy 子进程、仅本轮的 ADB forward 和远端临时 jar。不会自动 adb connect、不会 IP 回退、不会自行建立后台会话。首版不包含触摸、键盘、声音、录屏或自动重连。

当前 M2-00-E 只有代码/离线测试验证，尚不能声称浏览器持续画面已在 FNOS 真机通过。横竖屏变化会改变 MP4 视频轨尺寸，第一版提示停止并重新开始，后续再做不间断旋转适配；不承诺已量化的真实延迟和 60 FPS。

HTTP 本身不加密，适合你当前受信任的内网，不建议把该端口直接暴露公网；外网使用应另配 HTTPS/WSS。

现场验收：更新 M2 → 重新加载页面 → 手动连接 PJZ110 → 先选基础档点击「开始实时画面」→ 验证画面连续和手动停止 → 再试原生档。失败时只需返回页面错误文字和浏览器型号，不要发送 Token、.env 或视频数据。
### FNOS 首次实时画面故障：WebSocket 网络错误（代码修复，待现场复测）

首次用户反馈「实时视频 WebSocket 发生网络错误」。静态核对发现原镜像 `server/requirements.txt` 仅依赖基础版 `uvicorn`，遗漏 Uvicorn 进行实际 WebSocket HTTP Upgrade 所需的 `websockets` 或 `wsproto` 后端。之前的视频实验是普通 HTTP 请求，FastAPI TestClient 进程内模拟 WS 也不能证明 Docker 内的 Uvicorn 能进行真实网络握手。这是与现象一致的明确部署缺陷，但最终原因仍须以 FNOS 日志及重新部署后的复测判断。

已增加 `wsproto>=1.2,<2`，Docker Uvicorn 显式以 `--ws wsproto` 启动，遗漏依赖时启动失败而不是 HTTP 看似正常、WS 却无法升级。新增真实本地 TCP 握手测试：同源连接必须返回 `HTTP/1.1 101 Switching Protocols`，跨来源返回 403。页面细分握手失败、已连接尚未初始化和实际流中断，并提示检查 FNOS 日志。两种模式的部署脚本均需**重新构建镜像**才会安装依赖，单纯刷新浏览器无法修复老镜像。

建议复测：更新并重建 M2，重新加载页面，先用 HTTP + NAS IP 直连 EasyADB（避免未经配置的中间代理），手动连接 PJZ110，选择基础档开始实时画面。若仍失败，回传页面完整错误及 `sudo docker compose logs --tail=100 easyadb`（无代理模式加 `-f compose.no-proxy.yaml`）；只分享已脱敏日志，不分享 Token 或 `.env`。
### 播放引擎接口预留（本轮调整）

为了保持普通 HTTP + NAS IP 直接可用，当前正式测试入口**固定为 MSE**。将旧的内联播放器拆分为独立 `web/m2-player.js`，由 `EasyADBPlayers.create(kind, video, hooks)` 创建实例；播放器的基础契约是 `initialize(metadata)`、`append(chunk)`、`resume()`、`destroy()`。MSE 实例处理 MediaSource、SourceBuffer、播放追帧与缓冲清理，Web 页面的设备/鉴权/WebSocket 逻辑不负责直接操作这些对象。

`EasyADBPlayers.WebCodecsPlayer` 只提供相同接口的**显式未实现占位**，`capabilities().webcodecs.implemented` 恒为 `false`，不能选择也不能触发真实解码。未来先补 raw H.264 SPS/PPS/帧/时间戳协议，再接 `VideoDecoder` 和 Canvas，不能将当前 fMP4 分片直接交给 WebCodecs。

WebSocket 认证首条消息新增 `player: "mse"`。旧客户端省略该字段时为兼容仍按 MSE 处理；请求其他播放引擎将返回明确错误且**不会启动 ADB 或 scrcpy**。当前初始化事件明确返回 `player: "mse"`、`format: "fmp4"` 及动态 H.264 MIME。JS 文件由 `/m2-player.js` 提供并禁用缓存。首版仍以 MSE 实机效果为唯一验收目标，不声明 WebCodecs 已完成。

自动化除 Python / Shell / HTML 检查外，增加 Node 独立模块实际运行测试：验证 MSE 在 `sourceopen` 前到达视频字节时先入队、就绪后按顺序 append；验证释放/销毁及 WebCodecs 无法误启用。
## 后续技术路线（M2-01 及之后，未实现）

优先使用 scrcpy 官方项目发布的**同版本** client/server 作为技术参考/固定协议；其开发文档声明 client 与 server 通过视频、音频、控制等不同 socket 通信，视频 H.264 默认编码，协议属于内部实现、会随版本变化。M2 不将“任意 scrcpy-server 二进制 + 自写客户端”视为兼容。

参考：
- https://github.com/Genymobile/scrcpy
- https://github.com/Genymobile/scrcpy/blob/master/doc/develop.md
- https://github.com/Genymobile/scrcpy/blob/master/LICENSE

初步实验路径：固定完整版本和下载校验 → 在现有手动选中且已连接的 ADB serial 上使用会话专属隧道启动 server → 读取并解析对应版本视频元数据、帧头、编码格式 → 经认证的服务端会话转发 → 浏览器 WebCodecs H.264 解码与兼容性检查。若目标浏览器不支持所需解码能力，应明确提示，而不是错误地把截图定时轮播称为“实时视频”。控制通道须与同一个会话绑定，不能接受任意设备串号或任意 ADB shell 命令。使用官方源、审查 Apache-2.0 许可告知及分发义务；未固定版本/校验前不在 Dockerfile 自动下载或执行 scrcpy server。

## 必须继承的 M1 规则

- 只用 SQLite 中持久保存的 `selected_route` 和对应 `selected_serial`；不得自动优先内网、回退组网或定时重连。
- 会话只由已认证用户明确启动，选择变更后停止原会话；截图只使用所选设备的 serial。
- 只在会话确实运行期间允许用于检测**浏览器会话**的心跳；无人在线时不能残留设备控制进程/端口转发。容器重启后不得自行重建旧会话。
- 同一台设备的视频/控制通道必须隔离；默认单设备会话，双路功能放到 M2-06。
- FNOS 默认 Mihomo 模式与 `--no-proxy` 模式持续可用；不得更改原 `.env`、`./data/storage`、`./data/adb`。

## 首次从 M1 切到 M2 的 FNOS 操作

**不能只执行旧 M1 目录里的原部署脚本**：旧脚本会把工作区切回 M1。先由原 Git 登录用户（不要加 sudo）取得并切换 M2：

```sh
cd /vol3/1000/software/EasyADB
git status --short
git fetch origin
git switch feat/m2-web-control 2>/dev/null || git switch --track origin/feat/m2-web-control
git pull --ff-only origin feat/m2-web-control
sudo sh scripts/build-with-mihomo.sh
```

如 FNOS 环境本身由 OpenWrt 处理外网，最后一行可替换为：

```sh
sudo sh scripts/build-with-mihomo.sh --no-proxy
```

之后两种命令会调用 `scripts/update-m2.sh`，仅自动更新 `feat/m2-web-control`，保留 `--no-proxy` 参数；遇到本地脏文件或分支不能快进时停止，不重置用户代码和数据。
