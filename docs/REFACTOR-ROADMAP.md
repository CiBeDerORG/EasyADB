## 1. 现状架构判断与证据

当前组合技术选型合理，主要问题是跨层职责和状态修改入口不统一：

| 类别 | 现状与影响 | 主要代码 |
| --- | --- | --- |
| 应用入口过重 | `app.py` 约 1456 行，集路由、鉴权、业务协调、WS 会话、ADB 与资源生命周期于一体，改动牵连面大 | `server/app.py` |
| 跨模块并发 | 连接、投屏、切换线路部分已使用设备锁；设备基础信息修改和删除未始终使用同一锁，可能与连接/预留投屏交错 | `server/app.py`, `server/devices.py` |
| 锁和状态所有权 | 设备锁、会话注册表锁、OpenWrt 分组发现锁分散；需要统一锁顺序和责任边界 | `server/devices.py`, `server/m2_live.py`, `server/app.py` |
| 会话清理 | 清理未验证完成时保留占用是必要的安全设计，但恢复与资源预算需要专门治理 | `server/m2_live.py` |
| 20 路限制 | 20 是连接/会话数量上限，不等于同时运行时的 CPU、内存、队列与带宽预算；现有 20 路测试不代表真机压测 | `server/m2_live.py`, `tests/m2_twenty_contract.cjs` |
| 数据库 | SQLite 适合当前规模，但 schema 演进、事务、高频读取和模块写入责任需规范 | `server/store.py` |
| 凭据与安全 | OpenWrt 专用凭据目前按既有约定明文存 SQLite；解锁密码加密且本地存密钥；需要在后续版本完善文件权限、备份与威胁模型 | `server/store.py`, `server/m2_unlock.py` |
| 前端及媒体 | `web/index.html` 含较多内联逻辑，MSE/WebRTC 媒体链路和 WS 会话耦合 | `web/`, `server/m2_live.py`, `server/m2_webrtc.py` |
| 工程化 | CI/依赖锁定、稳定发布基线、部署回滚与环境健康检查仍可加强 | `.github/workflows/test.yml`, `Dockerfile`, `scripts/` |

已有可保留的良好基础：显式手动 ADB 操作、单设备锁、Session 所有权、清理失败不重用脏会话、受限媒体事件队列、scrcpy 版本/校验和、WS 同源和首消息认证、已有 Python/Node 测试。**不要为了拆文件而破坏这些既有约束。**

## 2. 目标架构（模块化单体）

```text
Web UI
   |
API / Router（HTTP、WS、鉴权、输入与响应）
   |
Service（业务编排、设备与会话操作）
   |
Infrastructure / Adapters（ADB、SQLite、媒体、OpenWrt）
```

建议目录随迁移逐步形成：

```text
server/
  app.py                  # 装配入口和 lifespan
  core/                   # 配置、生命周期与共用异常
  api/                    # 独立 Router；不承载复杂业务
  services/               # Device/Session/Control/Discovery 与操作协调
  infrastructure/         # ADB、SQLite/OpenWrt 等外部适配
  media/                  # 视频采集与各传输层（V4）
```

遵守 API → Service → Infrastructure 单向依赖；状态只有一个明确的写入所有者；同设备关键操作统一互斥、不同设备可以并发；锁顺序必须被测试固定，原则上设备锁先于注册表锁；资源必须有创建者/释放者；新结构先加兼容适配和测试，再迁移调用方。

## 3. 分版本计划

### V1：框架根基（当前工作）

| 编号 | 子任务 | 交付与完成判定 |
| --- | --- | --- |
| V1-01 | 基线与回归测试 | 固定 HTTP/WS 路由契约、认证与操作兼容测试；CI 覆盖重构分支 |
| V1-02 | 配置与初始化入口 | 启动参数统一校验，资源组装集中管理，生命周期显式；保持原测试注入/部署兼容 |
| V1-03 | 拆分 `app.py` | Router 分域，API 不直接承载业务实现；分批迁移，避免一次性挪动复杂 WS |
| V1-04 | Service 与异常规范 | 统一业务协调入口、底层错误与 HTTP 响应边界 |
| V1-05 | 设备操作协调 | 修改、删除、连接、线路变更与投屏预留遵循同一设备锁与稳定锁顺序；跨设备仍允许并发 |
| V1-06 | 完整回归 | 原有 API/WS、SQLite、部署、单设备和群控契约全部通过；列明未实测项目 |

V1 不重写 scrcpy、FFmpeg、WebRTC 底层，不改已有业务语义，不迁移数据库结构。

### V2：会话、并发与资源预算

将创建、占用、停止、验证清理和失败恢复纳入显式状态机；保留“未验证清理成功则不重用”原则；增加有界并发、容量/字节预算、异常断线与多设备压力测试。禁止把 20 路前端静态测试等同于 20 台真机验收。

### V3：数据与安全治理

SQLite 版本化迁移、事务边界与读写策略；凭据存储、文件/备份权限及日志脱敏；部署环境最小权限与鉴权/网络边界核查。现有 OpenWrt 密钥存储约定先记录、单独设计兼容迁移，避免静默破坏用户数据。

### V4：媒体与前端架构

视频采集和 MSE/WebRTC 传输适配分离，统一 WS 协议与关闭路径；拆分前端设备/群控/实时画面状态，保留现有页面与用户交互。

### V5：工程化交付

依赖与构建锁定、稳定发布分支、CI 分层、部署健康检查、回滚及日志可观测性。开发分支的自动部署与正式发布须有明确隔离。

## 4. 全程不可破坏的契约

1. 未认证的 REST 与 WS 不能操作设备；WS 不允许跨源握手，不把 token 放进 URL。
2. 不在页面加载或进程启动时进行隐藏的批量 ADB 连接、自动扫描或后台心跳；只在已有明确操作路径下调用。
3. 仅针对用户选择的设备与路由执行 ADB；不隐式切换地址、不跨设备发送控制。
4. 清理不完整的会话不得复用；投屏所有权与 Session ID 校验不被移除。
5. 已有 SQLite 数据原地兼容，环境变量/接口路径/请求字段与状态码尽量保持不变；行为改变须独立记录并增加测试。
6. 没有真机/真实 OpenWrt 环境的验证项明确标记「待实机验收」。

## 5. V1 关口

- Python/Node/壳脚本及已有 CI 全绿；新增的接口/鉴权/并发测试通过。
- `app.py` 作为装配入口而非主体业务实现，业务 API 可单独测试。
- 设备路由信息变更、删除、连接和投屏预留不会出现同设备交错状态；锁顺序有测试。
- 双设备操作仍可以并发；原视频/WS 行为不发生非预期变化。
- 原数据库原样升级，无须清空；部署配置兼容。
- 提交记录可按子任务追溯；实机测试清单与已验证内容分开。
